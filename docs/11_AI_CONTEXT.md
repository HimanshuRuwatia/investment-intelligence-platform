# 1. Purpose

When conflicts exist:

1. `PROJECT_CONTEXT.md` defines **why** the project exists.
2. `AI_CONTEXT.md` defines **how contributors should think** while implementing it.

This document intentionally repeats important constraints because AI coding assistants may not load every document simultaneously.

# 7. Canonical Terminology

The following words have one specific meaning throughout the project.

Do not invent synonyms.

## Raw Data

Information collected from external sources.

Examples:

* NAV history
* Holdings
* News
* RBI announcements

---

## Metric

A deterministic numerical value.

Examples:

* CAGR
* Sharpe Ratio
* Drawdown

Metrics are always reproducible.

---

## Evidence

Structured information generated from metrics.

Evidence supports conclusions.

Evidence is never generated by an LLM.

---

## Signal

A meaningful relationship detected from evidence.

Signals explain what changed.

---

## Knowledge

Long-term observations accumulated from repeated signals.

Knowledge persists over time.

---

## Insight

Human-readable explanation produced by the LLM.

Insights are generated from:

* Evidence
* Signals
* Knowledge

Never from raw data alone.

---

## Plugin

A business capability.

Examples:

* Performance
* Risk
* Macro

Plugins own their own implementation.

---

## Platform Core

Shared infrastructure.

Responsibilities include:

* Plugin lifecycle
* Scheduling
* Configuration
* Evidence storage
* Orchestration

The Platform Core MUST NOT contain financial business logic.

---

# 8. Mandatory Constraints

The following constraints are non-negotiable.

* Analyzers MUST NOT call LLMs.
* Collectors MUST NOT call LLMs.
* Plugins MUST remain independent.
* Plugins MUST NOT directly depend on other plugins.
* Business logic MUST NOT exist in APIs.
* Business logic MUST NOT exist in UI components.
* Evidence MUST be deterministic.
* Scores MUST be deterministic.
* The LLM MUST NOT calculate financial metrics.
* Frontend decisions MUST be postponed until the intelligence engine is stable.

If implementation conflicts with any of these rules, stop and reconsider the design.

# 11. Plugin Contract

Every business capability in the platform MUST be implemented as a Plugin.

A Plugin represents a single business domain.

Examples include:

* Performance
* Risk
* Consistency
* Benchmark
* Holdings
* Strategy
* Manager
* Macro
* News
* Behaviour

Plugins MUST be independently understandable.

A developer or AI assistant should be able to understand one plugin without reading every other plugin.

---

## Plugin Responsibilities

A Plugin MAY contain:

* Collectors
* Normalizers
* Analyzers
* Detectors
* Knowledge Builders
* MCP Tools
* API Endpoints
* Scheduled Jobs
* Configuration
* Tests

A Plugin MUST own all code related to its business capability.

---

## Plugin MUST NOT

A Plugin MUST NOT:

* Import business logic from another plugin.
* Modify another plugin's data.
* Depend on another plugin's internal implementation.
* Assume execution order of other plugins.
* Call another plugin's analyzers directly.

Plugins communicate only through shared platform services and structured data contracts.

# 12. Component Responsibilities

The following responsibilities are fixed.

---

## Collector

Purpose:

Acquire raw data.

Responsibilities:

* Fetch data
* Validate responses
* Handle retries
* Normalize transport formats

Collector MUST NOT:

* Perform financial analysis
* Calculate metrics
* Generate evidence
* Call LLMs

---

## Normalizer

Purpose:

Convert external data into internal domain models.

Responsibilities:

* Normalize field names
* Validate structure
* Standardize units
* Handle missing values

Normalizer MUST NOT:

* Perform business analysis
* Generate scores
* Detect signals

---

## Analyzer

Purpose:

Produce deterministic financial metrics.

Examples:

* CAGR
* Rolling Returns
* Sharpe Ratio
* Maximum Drawdown

Analyzer MUST:

* Be deterministic
* Be independently testable
* Produce reproducible outputs

Analyzer MUST NOT:

* Call LLMs
* Generate explanations
* Fetch external data

---

## Detector

Purpose:

Identify meaningful relationships.

Examples:

* Trend changes
* Sector rotation
* Strategy shifts

Detector consumes Evidence.

Detector produces Signals.

---

## Knowledge Builder

Purpose:

Accumulate repeated Signals into long-term Knowledge.

Knowledge should evolve gradually.

Knowledge MUST be evidence-backed.

Knowledge MUST NOT be invented.

---

## Reasoning Layer

Purpose:

Prepare optimized context for the LLM.

Responsibilities:

* Collect evidence
* Collect signals
* Collect knowledge
* Remove redundancy
* Prioritize important facts
* Build structured context

The Reasoning Layer MUST NOT calculate financial metrics.

---

## LLM

Purpose:

Communicate.

The LLM SHOULD:

* Explain
* Summarize
* Compare
* Answer "Why?"
* Generate reports

The LLM MUST NOT:

* Calculate metrics
* Override deterministic outputs
* Invent evidence
* Modify platform state

# 15. Coding Standards

The following standards should be followed consistently.

* Prefer explicit code over clever code.
* Keep functions small and focused.
* Keep classes focused on one responsibility.
* Use descriptive names.
* Avoid unnecessary abstractions.
* Prefer composition over inheritance.
* Strong typing is preferred.
* Minimize mutable shared state.
* Keep deterministic code pure whenever practical.

Consistency is more valuable than individual coding style.

---

# 16. Common AI Mistakes

AI coding assistants frequently make the following mistakes.

Avoid them.

❌ Mixing business logic into API handlers.

❌ Allowing analyzers to fetch data.

❌ Calling LLMs inside deterministic calculations.

❌ Sharing implementation details between plugins.

❌ Introducing unnecessary design patterns.

❌ Building UI before the platform works locally.

❌ Optimizing for distributed systems too early.

❌ Creating generic abstractions before there are multiple concrete implementations.

When in doubt, implement the simplest solution that satisfies current requirements.

# 20. AI Workflow

When implementing any feature, AI coding assistants SHOULD follow this workflow.

Step 1

Understand the problem.

Step 2

Identify the owning Plugin.

Step 3

Identify the responsible component.

Step 4

Implement only that responsibility.

Step 5

Write tests.

Step 6

Verify deterministic behaviour.

Step 7

Integrate with existing interfaces.

Step 8

Stop.

Avoid implementing future features that are not required for the current task.
