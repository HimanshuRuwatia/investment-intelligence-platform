# 1. Purpose

The Decision Engine is responsible for transforming deterministic financial information into structured investment evaluations.

The Decision Engine consumes:

* Evidence
* Signals
* Knowledge

and produces:

* Scores
* Rankings
* Confidence
* Decision Packages

The Decision Engine does **not** provide investment advice.

It evaluates available information in a consistent, explainable, and deterministic manner.

---

# 2. Responsibilities

The Decision Engine MUST:

* Evaluate deterministic information.
* Calculate Scores.
* Rank comparable funds.
* Calculate Confidence.
* Explain score composition.
* Produce Decision Packages.

The Decision Engine MUST NOT:

* Fetch external data.
* Perform LLM reasoning.
* Generate natural-language explanations.
* Ignore supporting Evidence.

---

# 3. Decision Philosophy

The Platform evaluates investments using evidence-based reasoning.

The Decision Engine should answer questions such as:

* Which fund demonstrates stronger historical performance?
* Which fund has lower downside risk?
* Which manager demonstrates greater consistency?
* Which strategy has historically performed well under similar market conditions?

The Decision Engine evaluates.

It does not recommend.

---

The Decision Engine consumes deterministic outputs generated by Plugins.

     ▼

# 5. Decision Package

The Decision Package is the canonical output of the Decision Engine.

Every Decision Package SHOULD contain:

* Individual Scores
* Overall Score
* Ranking
* Confidence
* Supporting Evidence
* Supporting Signals
* Supporting Knowledge
* Strengths
* Weaknesses
* Warnings
* Metadata

The Decision Package is deterministic.

It contains no natural-language reasoning generated by an LLM.

---

# 6. Why a Decision Package Exists

A numerical score alone is insufficient.

Example:

Performance Score

91

This raises questions.

Why 91?

Which Metrics contributed?

Which Signals increased the score?

Which Signals reduced the score?

How confident is the Platform?

The Decision Package answers these questions directly.

The LLM explains the Decision Package rather than reconstructing it.

---

# 7. Evaluation Principles

Every evaluation SHOULD satisfy the following principles.

Objectivity

Evaluations are based on deterministic information.

---

Explainability

Every conclusion references supporting Evidence.

---

Consistency

Identical inputs produce identical evaluations.

---

Traceability

Every score can be traced to its supporting information.

---

Reproducibility

Evaluations can be regenerated using the same deterministic inputs.

---

# 8. Evaluation Scope

The Decision Engine evaluates multiple dimensions independently.

Examples include:

* Performance
* Consistency
* Risk
* Portfolio Quality
* Fund Management
* Macro Resilience

Each dimension produces its own Score.

Dimensions remain independent before aggregation.

The initial Platform version evaluates the following categories.

| Category          | Weight |
| ----------------- | ------ |
| Performance       | 25%    |
| Consistency       | 20%    |

| Manager Quality   | 12%    |

---

# 10. Category Independence

Each category SHOULD be evaluated independently.

Example:

Performance

Should not directly depend on:

Macro Score.

Risk

Should not directly depend on:

Portfolio Score.

Every category evaluates one business concern.

Aggregation occurs only after category evaluation.

# 11. Overall Score

The Overall Score summarizes all category evaluations.

The Overall Score is calculated from weighted deterministic Scores.

The Overall Score SHOULD remain explainable.

The Platform should always be able to answer:

* Which category contributed most?
* Which category reduced the score?
* Which Evidence supports each category?

The Overall Score is an aggregation rather than a replacement for category Scores.

# 13. Score Architecture

## Purpose

The Decision Engine evaluates every fund across multiple independent dimensions.

Each dimension measures one aspect of investment quality.

The dimensions are evaluated independently before being combined into an Overall Score.

This separation improves explainability and allows the scoring methodology to evolve without redesigning the Platform.

---

# 14. Score Hierarchy

The Platform evaluates information using a hierarchical scoring model.

```text
Overall Score
        │
        ├── Performance Score
        ├── Consistency Score
        ├── Risk Score
        ├── Manager Quality Score
        ├── Portfolio Quality Score
        └── Macro Resilience Score
```

Each category score is calculated independently.

The Overall Score is an aggregation of these category scores.

---

# 15. Category Score Structure

Every category SHOULD be evaluated using smaller deterministic sub-factors.

The Platform evaluates:

```text
Category

↓

Sub-Factors

↓

Category Score

↓

Overall Score
```

Sub-factors improve:

* Explainability
* Traceability
* Future extensibility

---

# 16. Performance Score

**Weight: 25%**

The Performance Score evaluates historical return quality.

Example sub-factors:

| Sub-Factor               | Purpose                                     |
| ------------------------ | ------------------------------------------- |
| Long-Term CAGR           | Measure sustained wealth creation           |
| Rolling Returns          | Measure consistency over multiple periods   |
| Benchmark Outperformance | Compare against benchmark                   |
| Downside Capture         | Evaluate performance during market declines |
| Recovery Speed           | Evaluate recovery after corrections         |

The exact calculation methodology should remain deterministic and versioned.

---

# 17. Consistency Score

**Weight: 20%**

The Consistency Score evaluates the stability of historical performance.

Example sub-factors:

| Sub-Factor                    | Purpose                                  |
| ----------------------------- | ---------------------------------------- |
| Rolling Return Stability      | Measure variation across rolling periods |
| Return Persistence            | Measure repeated outperformance          |
| Drawdown Recovery Consistency | Measure reliability after declines       |
| Category Ranking Stability    | Measure long-term competitiveness        |

Consistency rewards repeatability rather than isolated success.

---

# 18. Risk Score

**Weight: 18%**

The Risk Score evaluates downside characteristics.

Example sub-factors:

| Sub-Factor         | Purpose                             |
| ------------------ | ----------------------------------- |
| Volatility         | Measure return variability          |
| Maximum Drawdown   | Measure worst historical decline    |
| Sharpe Ratio       | Risk-adjusted return                |
| Sortino Ratio      | Downside risk-adjusted return       |
| Downside Deviation | Measure negative return variability |

Risk evaluates the quality of returns rather than their magnitude alone.

---

# 19. Manager Quality Score

**Weight: 12%**

The Manager Quality Score evaluates characteristics of the fund management process.

Example sub-factors:

| Sub-Factor                  | Purpose                                  |
| --------------------------- | ---------------------------------------- |
| Strategy Consistency        | Evaluate adherence to stated philosophy  |
| Portfolio Stability         | Measure unnecessary turnover             |
| Historical Decision Quality | Evaluate repeated successful positioning |
| Leadership Continuity       | Measure manager stability                |

Manager evaluation should rely on deterministic evidence wherever practical.

---

# 20. Portfolio Quality Score

**Weight: 15%**

The Portfolio Quality Score evaluates the current portfolio rather than historical returns.

Example sub-factors:

| Sub-Factor                | Purpose                    |
| ------------------------- | -------------------------- |
| Diversification           | Portfolio concentration    |
| Sector Allocation         | Exposure balance           |
| Market Capitalization Mix | Small/Mid/Large allocation |
| Holding Quality           | Portfolio composition      |
| Portfolio Turnover        | Stability of holdings      |

Portfolio analysis complements historical performance.

---

# 21. Macro Resilience Score

**Weight: 10%**

The Macro Resilience Score evaluates how a fund behaves under changing macroeconomic conditions.

Example sub-factors:

| Sub-Factor                | Purpose                                 |
| ------------------------- | --------------------------------------- |
| Inflation Sensitivity     | Performance during inflationary periods |
| Interest Rate Sensitivity | Response to monetary policy changes     |
| GDP Cycle Behaviour       | Performance across economic cycles      |
| Market Stress Behaviour   | Performance during market corrections   |

This category is intentionally smaller because macro conditions change over time.

---

# 22. Score Normalization

Different Metrics operate on different numerical scales.

Examples:

CAGR

Percentage

Sharpe Ratio

Unitless

Drawdown

Negative percentage

The Decision Engine MUST normalize all sub-factor values before aggregation.

Normalization ensures fair comparison across categories.

The normalization algorithm should be deterministic and versioned.

---

Category scores are combined using documented weights.

Example:

```text
Overall Score

=

+

Consistency × 20%

+

Risk × 18%

+

Manager × 12%

+

Portfolio × 15%

+

Macro × 10%
```

The aggregation process must remain deterministic.

# 24. Explainability Requirements

Every category score MUST be explainable.

For every category, the Platform should be able to answer:

* Which sub-factors contributed positively?
* Which sub-factors contributed negatively?
* Which Evidence supports each sub-factor?
* How confident is the evaluation?

The Decision Engine should never produce an unexplained score.

---

# 25. Score Evolution

The scoring framework is expected to evolve.

Examples of acceptable evolution include:

* Adding new sub-factors.
* Improving weighting within a category.
* Improving normalization algorithms.

The overall architecture should remain stable.

Methodology changes should be versioned and documented.

---

# 26. Score Summary

The Platform evaluates funds using multiple independent categories.

Each category is evaluated using deterministic sub-factors.

Category scores are normalized and aggregated into an Overall Score.

The scoring framework prioritizes explainability over simplicity.

Every score should be reproducible, traceable, and supported by deterministic evidence.

# 27. Confidence Architecture

## Purpose

Confidence represents how strongly the available deterministic information supports a conclusion.

Confidence is independent of the Score.

A high Score does not necessarily imply high Confidence.

Likewise, a low Score may still have high Confidence.

The Platform should communicate both separately.

---

# 28. Confidence Philosophy

The Platform distinguishes between:

**Evaluation**

"What does the available information suggest?"

and

**Confidence**

"How strongly should we trust that evaluation?"

These concepts must remain separate throughout the Platform.

---

# 29. Confidence Hierarchy

Confidence is calculated progressively throughout the processing pipeline.

```text id="l39wzp"
Metric Confidence
        │
        ▼
Evidence Confidence
        │
        ▼
Signal Confidence
        │
        ▼
Knowledge Confidence
        │
        ▼
Category Confidence
        │
        ▼
Overall Confidence
```

Confidence should never increase without additional supporting information.

As information becomes more abstract, confidence should generally remain the same or decrease unless strengthened by multiple independent sources.

---

# 30. Metric Confidence

Metric Confidence reflects confidence in deterministic calculations.

Examples influencing Metric Confidence include:

* Completeness of source data
* Successful validation
* Data freshness
* Calculation integrity

Metric Confidence is generally expected to be high because calculations are deterministic.

---

# 31. Evidence Confidence

Evidence Confidence reflects the quality of supporting Metrics.

Examples include:

* Number of supporting Metrics
* Agreement between Metrics
* Data coverage
* Historical completeness

Evidence should always reference the Metrics contributing to its confidence.

---

# 32. Signal Confidence

Signal Confidence reflects the strength of an observed pattern.

Examples:

High Confidence

* Trend observed consistently over multiple periods.

Lower Confidence

* Trend observed only once.

Signals supported by multiple independent Evidence records should generally receive higher confidence than Signals supported by a single observation.

---

# 33. Knowledge Confidence

Knowledge Confidence measures confidence in long-term understanding.

Examples of factors include:

* Number of supporting Signals
* Historical duration
* Stability over time
* Consistency across market cycles

Knowledge should become stronger through repeated confirmation rather than isolated success.

---

# 34. Category Confidence

Each category score SHOULD have its own confidence.

Examples:

Performance Confidence

Risk Confidence

Portfolio Confidence

Manager Confidence

Macro Confidence

Categories should calculate confidence independently.

One weak category should not reduce confidence in unrelated categories.

---

# 35. Overall Confidence

Overall Confidence summarizes confidence across the entire Decision Package.

Overall Confidence should consider:

* Category Confidence
* Data completeness
* Data freshness
* Breadth of supporting Evidence
* Breadth of supporting Knowledge

Overall Confidence should not simply average category confidences.

The aggregation methodology should be deterministic and documented.

---

# 36. Confidence Factors

The following factors MAY influence confidence.

| Factor                                | Effect   |
| ------------------------------------- | -------- |
| Longer historical coverage            | Increase |
| Higher data completeness              | Increase |
| Multiple independent Evidence records | Increase |
| Consistent Signals                    | Increase |
| Stable Knowledge over time            | Increase |
| Missing data                          | Decrease |
| Conflicting Evidence                  | Decrease |
| Stale information                     | Decrease |
| Validation failures                   | Decrease |

Confidence should always be evidence-based.

---

# 37. Confidence Propagation

Confidence propagates through the Platform.

```text id="6r2fjg"
Metrics
      │
      ▼
Evidence
      │
      ▼
Signals
      │
      ▼
Knowledge
      │
      ▼
Scores
      │
      ▼
Decision Package
```

Each stage should preserve the confidence of its inputs while applying its own documented methodology.

Confidence propagation should remain deterministic.

---

# 38. Conflicting Evidence

Deterministic systems may encounter conflicting Evidence.

Example:

Performance Plugin

Strong positive Evidence.

Risk Plugin

Strong negative Evidence.

The Decision Engine should preserve both.

Conflicts should be represented explicitly rather than hidden.

The LLM should explain the conflict rather than resolving it independently.

---

# 39. Missing Information

Missing information should reduce confidence rather than producing assumptions.

Examples include:

* Missing holdings data.
* Incomplete NAV history.
* Unavailable benchmark data.
* Missing macroeconomic observations.

The Platform should acknowledge uncertainty.

It should never fabricate certainty.

---

# 40. Decision Package Confidence

Every Decision Package SHOULD include:

* Overall Confidence
* Category Confidence
* Confidence Drivers
* Confidence Limitations

Examples of Confidence Drivers:

* Twenty years of NAV history.
* Stable historical data.
* Consistent benchmark availability.

Examples of Confidence Limitations:

* Manager history available for only three years.
* Holdings unavailable for two quarters.

This enables transparent evaluation.

---

# 41. Confidence Explainability

The Platform should always be able to answer:

* Why is confidence high?
* Why is confidence low?
* Which evidence increased confidence?
* Which limitations reduced confidence?

Confidence should be explainable using deterministic information.

---

# 42. LLM Responsibilities

The LLM communicates confidence.

The LLM does not calculate confidence.

Example:

Good

"Performance confidence is high because the evaluation is supported by twenty years of validated NAV history and consistent rolling return behaviour."

Poor

"I'm highly confident this fund will outperform."

The latter predicts the future.

The Platform evaluates available evidence.

It does not predict future outcomes.

---

# 43. Confidence Summary

Confidence is a first-class output of the Decision Engine.

Confidence accompanies every important evaluation.

Confidence reflects the strength of supporting deterministic information rather than subjective certainty.

The Platform should encourage users to consider both the Score and the Confidence before interpreting any evaluation.

Separating evaluation from confidence is one of the Platform's core architectural principles.

# 44. Ranking Engine

## Purpose

The Ranking Engine compares funds using deterministic evaluations produced by the Decision Engine.

The objective is to produce rankings that are:

* Explainable
* Stable
* Reproducible
* Evidence-backed

Rankings are descriptive.

They are not investment recommendations.

---

# 45. Ranking Philosophy

The Platform ranks funds based on deterministic analysis.

The ranking answers:

* Which fund currently demonstrates stronger characteristics?
* Why is it ranked higher?
* Which categories contributed most?
* Which categories reduced its position?

The Platform SHOULD always be able to justify every ranking position.

---

# 46. Ranking Scope

Rankings should always occur within a defined scope.

Examples include:

Category Rankings

* Large Cap
* Mid Cap
* Small Cap
* Flexi Cap
* ELSS

Asset Class Rankings

* Mutual Funds
* ETFs

Custom User Collections

* User Watchlist
* User Portfolio
* Shortlisted Funds

Funds from unrelated categories SHOULD NOT be ranked together by default.

---

# 47. Ranking Inputs

The Ranking Engine consumes deterministic outputs only.

Required inputs include:

* Overall Score
* Category Scores
* Confidence
* Decision Package

Optional inputs include:

* Data Freshness
* Evidence Quality
* Coverage

The Ranking Engine MUST NOT consume raw market data directly.

---

# 48. Ranking Process

The ranking process follows a deterministic sequence.

```text id="m7r4x2"
Decision Packages
        │
        ▼
Eligibility Validation
        │
        ▼
Ranking Scope Selection
        │
        ▼
Sorting
        │
        ▼
Tie Resolution
        │
        ▼
Ranking Explanation
```

Each stage has one responsibility.

---

# 49. Eligibility Validation

Before ranking, each fund should be validated.

Examples of validation include:

* Required category available.
* Required Scores available.
* Minimum historical data available.
* Minimum Confidence threshold met.

Funds that fail validation should not receive a ranking.

Instead, the Platform should explain why the fund was excluded.

---

# 50. Primary Ranking

The default ranking order is determined by:

1. Overall Score
2. Overall Confidence
3. Evidence Quality
4. Data Freshness

This ordering ensures that a slightly higher score supported by significantly weaker evidence does not automatically dominate a better-supported evaluation.

---

# 51. Tie Resolution

Identical Overall Scores are expected.

Tie resolution should follow deterministic rules.

Recommended order:

1. Higher Confidence
2. Higher Performance Score
3. Higher Consistency Score
4. Lower Risk
5. Better Evidence Quality
6. Fresher data

If all values remain equal, both funds should share the same ranking position.

The Platform MUST NOT invent arbitrary differences.

---

# 52. Ranking Stability

The Platform should minimize unnecessary ranking changes.

Small fluctuations should not constantly reorder rankings.

Examples:

Fund A

91.23

Fund B

91.20

The Platform may indicate that the funds are effectively equivalent rather than emphasizing an insignificant difference.

Ranking stability improves user trust.

---

# 53. Ranking Bands

Rather than treating every numerical difference equally, the Platform SHOULD classify funds into ranking bands.

Example:

| Overall Score | Band        |
| ------------: | ----------- |
|        90–100 | Exceptional |
|         80–89 | Strong      |
|         70–79 | Good        |
|         60–69 | Average     |
|      Below 60 | Weak        |

Bands provide more intuitive interpretation than raw scores alone.

The exact thresholds are part of the scoring methodology and should be versioned.

---

# 54. Comparative Analysis

The Ranking Engine should identify key differentiators between comparable funds.

Example:

Fund A

* Better Performance
* Better Consistency

Fund B

* Lower Risk
* Stronger Portfolio Quality

The Platform should compare strengths and weaknesses rather than only numerical scores.

---

# 55. Ranking Explanation

Every ranking SHOULD include structured reasoning.

The explanation SHOULD answer:

* Why is this fund ranked here?
* Which categories contributed most?
* Which categories reduced the ranking?
* Which evidence supports the evaluation?
* How confident is the Platform?

Ranking explanations remain deterministic.

The LLM converts them into natural language.

---

# 56. Decision Package Extension

The Decision Package SHOULD include ranking information.

Recommended fields include:

* Overall Rank
* Category Rank
* Ranking Band
* Ranking Drivers
* Ranking Limitations

This allows downstream components to explain rankings without recalculating them.

---

# 57. Ranking Limitations

The Platform should explicitly communicate ranking limitations.

Examples include:

* Limited historical data.
* Missing holdings information.
* Recently launched fund.
* Insufficient benchmark history.

Limitations improve transparency.

They should not be hidden from the user.

---

# 58. Ranking Evolution

The ranking methodology is expected to evolve.

Examples include:

* Improved tie-breaking.
* Better normalization.
* Additional ranking dimensions.
* New asset classes.

Methodology changes SHOULD be versioned.

Historical rankings should remain reproducible.

---

# 59. Ranking Summary

The Ranking Engine transforms deterministic evaluations into ordered comparisons.

Rankings are:

* Evidence-backed
* Explainable
* Stable
* Reproducible

Every ranking should be accompanied by deterministic reasoning rather than relying on unexplained numerical ordering.

Ranking is an extension of evaluation, not a replacement for it.

# 60. Decision Package Specification

1. What did the Platform conclude?

2. Why did it reach that conclusion?

3. How strongly does the available evidence support the conclusion?

Every Decision Package should answer all three.

# 78. Conflict Resolution

## Purpose

The Decision Engine is responsible for resolving conflicting deterministic evaluations.

Conflicting evidence is expected.

The Platform should preserve conflicting information rather than hiding it.

Conflict resolution exists to produce a balanced evaluation while maintaining explainability.

---

# 79. Conflict Philosophy

Conflicting Evidence is not an error.

It is valuable information.

Example:

Performance

Excellent

Risk

Poor

Portfolio Quality

Strong

Macro Resilience

Weak

The Platform should communicate this balance rather than attempting to simplify it into a single narrative.

---

# 80. Types of Conflicts

The Platform recognizes several types of conflicts.

## Category Conflict

Different category scores disagree.

Example:

Performance

95

Risk

58

---

## Evidence Conflict

Different Evidence supports opposing conclusions.

Example:

Evidence A

Consistent long-term growth.

Evidence B

Recent deterioration.

---

## Signal Conflict

Signals point in different directions.

Example:

Positive Momentum.

Increasing Volatility.

---

## Knowledge Conflict

Historical Knowledge differs from recent observations.

Example:

Historically conservative strategy.

Recent aggressive allocation.

---

## Data Conflict

Different providers or datasets disagree.

Example:

Benchmark classification differs across providers.

The Platform should preserve the discrepancy until resolved.

---

# 81. Conflict Handling Principles

The Platform SHOULD:

* Preserve all deterministic information.
* Record conflicting observations.
* Explain the conflict.
* Avoid arbitrary resolution.
* Allow the LLM to communicate the trade-offs.

The Platform MUST NOT:

* Ignore conflicting Evidence.
* Invent missing information.
* Hide uncertainty.

---

# 82. Category Independence

Category Scores remain independent.

Example:

High Performance should never automatically increase Risk Score.

Likewise,

Poor Macro conditions should not directly reduce Portfolio Quality.

Categories influence the Overall Score through weighting rather than direct modification.

---

Positive Contributors

* Excellent diversification.

Negative Contributors

Examples:

* High drawdown.
* Increasing volatility.
* Weak downside protection.

The Platform should expose both.

---

# 84. Decision Drivers

Example:

Primary Positive Drivers

Primary Negative Drivers

* Elevated portfolio concentration

Decision Drivers become one of the most valuable inputs for the Reasoning Layer.

Many funds involve trade-offs.

# 86. Decision Consistency

Given identical deterministic inputs,

the Decision Engine MUST always produce:

* The same Scores
* The same Rankings
* The same Decision Package

No randomness is permitted.

---

# 87. Policy Versioning

Every evaluation MUST reference the policies used.

Examples:

Scoring Policy

Version 1.2

Ranking Policy

Version 1.0

Normalization Policy

Version 1.1

Future changes to methodology should create new policy versions rather than silently changing historical evaluations.

# 90. Decision Engine Quality Attributes

The Decision Engine SHOULD satisfy the following quality attributes.

| Attribute     | Description                                       |
| ------------- | ------------------------------------------------- |
| Deterministic | Same input produces same output                   |
| Explainable   | Every conclusion is traceable                     |
| Modular       | New scoring dimensions can be added independently |
| Versioned     | Methodology changes are recorded                  |
| Testable      | Every policy can be unit tested                   |
| Transparent   | Trade-offs remain visible                         |
| Reproducible  | Historical evaluations can be regenerated         |

These attributes are considered core architectural requirements.

# 92. Decision Engine Summary

The Decision Engine is the deterministic intelligence layer of the Investment Intelligence Platform.

It transforms:

* Evidence
* Signals
* Knowledge

into:

* Scores
* Rankings
* Confidence
* Decision Packages

using transparent, reproducible, and explainable methodologies.

The Decision Engine never predicts the future.

It evaluates available evidence and communicates the strengths, weaknesses, confidence, and limitations of that evaluation in a structured form.

This deterministic evaluation becomes the foundation for every explanation generated by the LLM.
